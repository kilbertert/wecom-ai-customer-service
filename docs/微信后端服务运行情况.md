  服务运行方式

  不是 systemd 托管，不是 Docker，不是 supervisor，是 用户态脚本启动的裸 uvicorn 进程。

  启动脚本：/root/start_uvicorn.sh

  每次"重启"本质是跑这个 bash 脚本，它做 3 件事：

  #!/bin/bash
  PROJECT_DIR="/root/ai-customer/wecom-ai-customer-service-main"
  PYTHON="$PROJECT_DIR/venv/bin/python3"

  # 1. 杀旧进程 (强制 SIGKILL)
  pkill -9 -f "uvicorn app.main:app" 2>/dev/null
  sleep 1

  # 2. 清 .pyc 缓存 (防旧代码生效)
  find "$PROJECT_DIR" -name "*.pyc" -delete
  find "$PROJECT_DIR" -name "__pycache__" -type d -exec rm -rf {} + 2>/dev/null

  # 3. setsid + nohup 后台启动 uvicorn
  cd "$PROJECT_DIR"
  setsid nohup "$PYTHON" "$PROJECT_DIR/run_uvicorn.py" \
      >> /tmp/uvicorn.log 2>&1 &

  关键点：
  - setsid 创建新会话，让 uvicorn 进程脱离父 SSH 进程（否则 SSH 退出 uvicorn 也死）
  - nohup 忽略 SIGHUP
  - 所有输出重定向到 /tmp/uvicorn.log（你一直在 tail 的那个文件）
  - cd 进项目目录是关键 — .env 加载、相对路径模块都依赖这个 cwd（这是 uvicorn cwd 陷阱的根因，过去踩过坑）

  入口脚本：/root/ai-customer/.../run_uvicorn.py

  不是直接 uvicorn app.main:app。先跑一个 wrapper Python 脚本，做：

  import os
  os.chdir("/root/ai-customer/wecom-ai-customer-service-main")  # 强制 cwd
  import sys
  sys.path.insert(0, ".")  # 让 `from app.xxx import xxx` 能找到
  from app.main import app  # 触发 settings 加载
  # 然后 uvicorn.run(app, ...) 启动

  为什么需要 wrapper：
  - uvicorn 进程需要 cwd 是项目根目录（.env 在那里）
  - cd 在 shell 层 + os.chdir 在 Python 层是双重保险
  - 这样即使你忘了在哪个目录执行 bash /root/start_uvicorn.sh，cwd 也保证正确

  进程生命周期

  SSH 登录 → bash /root/start_uvicorn.sh
                  ↓
          pkill 旧进程
          清 pyc 缓存
          setsid nohup 启动新进程（脱离 SSH）
                  ↓
          立刻返回（不阻塞）
                  ↓
          SSH 退出，新进程继续跑（因为 setsid + nohup）
                  ↓
          新进程死掉的唯一情况：
            - 手动 pkill
            - 机器重启
            - OOM / 段错误

  意味着：你重启 SSH 不会影响服务（这跟 systemd 一样稳定，但更脆弱 — 没有 watchdog）。
